# Why the Java Jpss native solution does not work?

The reason SSH can access the Kerberos ticket in the LSA while your HDFS (Java) client cannot comes down to Native vs. Non-Native integration.

When you use a Windows SSH client (like the built-in OpenSSH, PuTTY, or Tectia), it doesn't try to "read" the ticket data like Java does. Instead, it uses a native Windows API called SSPI (Security Support Provider Interface).

1. The "Black Box" Approach (SSPI)
Think of the LSA as a locked vault.

The HDFS/Java approach: Java acts like a locksmith. It asks the LSA, "Give me the keys (Session Key) inside the vault so I can build my own Kerberos packets." Windows sees this as a security risk and blocks standard users (Error 1312).

The SSH approach: SSH acts like a courier. It tells the LSA, "I have this data that needs to be signed for the server. You do the encryption inside your vault and just give me the result."

Because the sensitive Session Key never leaves the LSA's protected memory, Windows allows SSH to perform this action without requiring Administrator privileges or the allowtgtsessionkey registry hack.

2. Why Java behaves differently
Java’s default Kerberos implementation (the Krb5LoginModule) was originally written for Unix/Linux. On those systems, Kerberos tickets are just files on disk (ccache), so the Java code is designed to physically read the ticket file, parse the bytes, and manage the encryption itself.

When ported to Windows, Java tries to simulate this "file-reading" behavior by asking the LSA for the raw ticket data. Windows views this "raw data request" as much more dangerous than a "please sign this" request.

3. Can we make HDFS act like SSH?
In theory, yes. This is what the flag -Dsun.security.jgss.native=true was supposed to do. It tells Java to stop trying to be a "locksmith" and start acting like the "courier" (using the native Windows SSPI).

However, it usually fails in Hadoop because:

Library Mismatch: Hadoop's SASL implementation often expects the "raw" Kerberos data structures provided by the internal Java library.

GSS-API Wrapper: The "bridge" between Java and Windows SSPI (the sspibridge.dll) is notoriously buggy and often doesn't support the specific GSS-API extensions Hadoop needs for its RPC calls.

4. SSH "Forwarding" vs. HDFS Access
There is one more critical difference. When you SSH into a server, you are often performing Delegation.

If you are using SSH to jump from one Windows machine to another, the SSH client uses the GSSAPI to pass your identity. Windows LSA is specifically optimized for this native "handshake." HDFS, on the other hand, is a complex distributed system that requires "Service Tickets" for multiple components (Namenode, Datanodes), which involves more frequent and detailed interactions with the ticket cache than a single SSH connection.

# HDFS client with kerberos in Windows server

The cleanest ways to access a `Kerberized HDFS cluster` from Windows because `no keytab, no kinit, and no credential cache file` 
are required. The Java client uses the `Kerberos Ticket Granting Ticket (TGT)` that Windows stores in 
`LSASS (Local Security Authority Subsystem Service) through SSPI`. 

> `Oracle's` JDK supports this through its native GSS-API integration when enabled.
> 
Below is the complete architecture

```text
+-------------------------+
| Windows Server 2025     |
|                         |
| Logged in as            |
| user@MYDOMAIN.COM       |
|                         |
|        LSASS            |
|   Kerberos TGT          |
+-----------+-------------+
            |
            | SSPI
            |
+-----------v-------------+
| Java 17/21              |
| Native GSS              |
| sspi.dll                |
+-----------+-------------+
            |
            |
      Hadoop Client
            |
      UserGroupInformation
            |
      RPC SASL Kerberos
            |
+-----------v-------------+
| NameNode                |
| Kerberos                |
+-------------------------+
```

## Prerequisites

### Windows machine joined to Active Directory
### User has an account in AD and has a Kerberos TGT after login.
### HDFS client already configured for Kerberos 
```xml
<property>
    <name>hadoop.security.authentication</name>
    <value>kerberos</value>
</property>
```
and the service principal(e.g. nn/srv1.casd.fr, dn/srv2.casd.fr) for hdfs cluster must exist in `AD`.

## Steps to follow for enable kerberos via SSPI

### 1. Get the JDK with GSS support

All modern JDKs from Zulu, Oracle, supports native GSS, you should find `sspi_bridge.dll` in `zulu11.86.21-ca-jdk11.0.30-win_x64\bin`

### 2. Configure krb5.conf

Although authentication uses SSPI, Java needs to know your `Active Directory Realm`.

```ini
[libdefaults]
default_realm = MYDOMAIN.COM
udp_preference_limit = 1
ticket_lifetime = 24h
renew_lifetime = 7d
forwardable = true
default_tgs_enctypes = aes256-cts-hmac-sha1-96 aes128-cts-hmac-sha1-96
default_tkt_enctypes = aes256-cts-hmac-sha1-96 aes128-cts-hmac-sha1-96
permitted_enctypes = aes256-cts-hmac-sha1-96 aes128-cts-hmac-sha1-96

[realms]
MYDOMAIN.COM = {
kdc = dc01.mydomain.com
}

[domain_realm]
.mydomain.com = MYDOMAIN.COM
mydomain.com = MYDOMAIN.COM
```

### 3. configure core-site.xml

```xml
<configuration>

    <property>
        <name>fs.defaultFS</name>
        <value>hdfs://nn01.mydomain.com:8020</value>
    </property>

    <!-- Tell Hadoop the filesystem is secured with Kerberos -->
    <property>
        <name>hadoop.security.authentication</name>
        <value>kerberos</value>
    </property>
    
    <!-- Set RPC protection to authentication (or 'privacy' if data encryption is required) -->
    <property>
        <name>hadoop.rpc.protection</name>
        <value>authentication</value>
    </property>

</configuration>
```

### 4. Configure jaas.conf

`JAAS` is Java's framework for authentication and authorization.
Whenever a Java application needs to authenticate using technologies like:
- Kerberos
- LDAP
- Active Directory
- Smart Cards
- Custom authentication

it loads one or more `LoginModules` defined in a `JAAS configuration file`.

This file is the key that forces Java to stop using its pure-Java Kerberos implementation 
(which fails due to the registry key) and instead use the `Native Windows SSPI bridge`.


#### 4.1 JAAS configuration syntax

The general syntax is 

```text
ApplicationName {
    LoginModule Flag Options;
};
```

For example, in below configuration
- `Client` : application entry
- `Krb5LoginModule` : authentication module
- `required` : control flag
- `useTicketCache=true` : module option

```text
Client {
    com.sun.security.auth.module.Krb5LoginModule required
    useTicketCache=true;
};
```

#### 4.2 JAAS for JPSS configuration

In the below JAAS configuration file, we have two application entries:
- `initiate`: This entry is used whenever Java acts as a `Kerberos client`.
- `accept` : This entry is used whenever Java accepts and validates a `incoming Kerberos authentication request`.

```text
com.sun.security.jgss.krb5.initiate {
    com.sun.security.jgss.native required;
};

com.sun.security.jgss.krb5.accept {
    com.sun.security.jgss.native required;
};
```

For example, when a hdfs client try to list files in hdfs file system, it's the `initiate` block which will be used.
When a hdfs namenode receives a list files request, it's the `accept` block which will be used.

The below table shows possible flags of the jpss control flags

| Flag       | Meaning                                                                                   |
|------------|-------------------------------------------------------------------------------------------|
| required   | Must succeed, but continue processing other modules                                       |
| requisite  | Must succeed; if it fails, stop immediately                                               |
| sufficient | If it succeeds, authentication succeeds immediately (assuming no prior required failures) |
| optional   | Used only if no other modules determine the outcome                                       |


#### 4.3 JPSS vs Krb5loginModule

The native java kerberos module is `com.sun.security.auth.module.Krb5LoginModule`, it parses krb5.conf, reads keytabs, and reads ticket cache.
The krb authentication is 100% handled by jdk. As a result, you need to specify much information as options in `jaas.conf` file.

The below `jaas.conf` file is an example of a client with keytab configuration.
```text
Client {
    com.sun.security.auth.module.Krb5LoginModule required
    useKeyTab=true
    principal=user@REALM
    keyTab=/etc/security/keytabs/user.keytab
};
```

The JPSS module delegates the krb authentication to OS Kerberos authentication system. So everything is handled by the
OS, you don't need to put any options in the `jaas.conf`.

```text
Application
      |
      | GSS-API
      |
Java GSS
      |
      | reads JAAS
      |
com.sun.security.jgss.native
      |
Native GSS Library
      |
Windows Server (MIT Kerberos / Heimdal / SSPI)
      |
(Kerberos KDC)/AD
```

### 5. Setup JVM options

To load all the above configurations to JVM when running the HDFS CLI, you need to add the below options into JVM.

```text
# load jaas.conf file to jvm
-Djava.security.auth.login.config=C:\conf\jaas.conf

# load krb5.conf file to jvm
-Djava.security.krb5.conf=C:\krb5.conf

# Enable native GSS:
-Dsun.security.jgss.native=true

# Allow Java to obtain credentials from the native provider instead of requiring a JAAS Subject
-Djavax.security.auth.useSubjectCredsOnly=false
```

> The combination of `sun.security.jgss.native=true` and `javax.security.auth.useSubjectCredsOnly=false` is what 
> enables Java GSS to use the Windows SSPI credentials stored in LSASS

If you want to enable debug mode for jpss and krb5, you can add the two following line into jvm 

```text
-Dsun.security.jgss.debug=true
-Dsun.security.krb5.debug=true
```
> We recommend you to add these config into the `$HADOOP_HOME/etc/hadoop/hadoop-env.cmd` file. So when you run hdfs CLI
> commands, all these JVM options are loaded automatically.
> 
Below is a `hadoop-env.cmd` configuration example

```cmd
set HADOOP_OPTS=%HADOOP_OPTS% -Djava.security.krb5.conf="C:\hadoop\conf\krb5.ini" -Djava.security.auth.login.config="C:\hadoop\conf\jaas.conf" -Djavax.security.auth.useSubjectCredsOnly=false -Dsun.security.jgss.native=true
set HADOOP_CLIENT_OPTS=%HADOOP_OPTS%
```

## Workflow of a hdfs client call with kerberos ticket

```text
# user start a call of hdfs client
hdfs dfs -ls / Or FileSystem.get()
↓
# the CLI or java api will call the class DFSClient
DFSClient
↓
# the method SaslRpcClient will be called
SaslRpcClient
↓
# the class Java GSS will be called
JGSS
↓
# 
Native GSS
↓
# SSPI bridge will be called
SSPI
↓
# call windows LSASS
LSASS
↓
# if TGT exist in LSA, continue, if not, auth failed, stop all
Existing TGT
↓
# If service ticket not exist, request service ticket with TGT
Request service ticket
↓
# send service ticket to NameNode
NameNode
↓
# namenode check service ticket, if ok, auth success, if not, auth failed
Authentication succeeds
```
